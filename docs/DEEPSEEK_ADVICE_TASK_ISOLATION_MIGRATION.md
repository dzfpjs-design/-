# 建议记录库存的任务隔离：现状与迁移门槛

状态：调查和回归测试；未解除 1000 行限制，未启用终态只读展示。这里不授权连接实际数据库、处理真实资料或重发历史请求。

## 可复现事实

`test_advice_v2_large_actual_inventory_limit_pg.py` 只在专用临时 PostgreSQL 使用合成数据：1001 组 v1 历史分别包含关联的 Plan、Job、接受和取消审计，并逐一生成；真实读取器核对首尾历史，另有一条原始 v2 Plan。当前 `same_goal_advice_store_v302._rows` 和通用库存读取器均因 1000 行上限返回 409。现有其他模型行和审计行也各受该限制；1000 并不是可支持的请求次数承诺。

同一测试还在库存读方持有 Task 行锁时，从独立事务直接插入并提交带同一 task_id 的异常审计。再次读取能发现孤儿，但之前的扫描结果已过时。此测试证明 Task 行锁本身不能阻止未遵循约定的数据库写方；它不表示对外 API 已允许用户伪造这一审计。现有试验使用的表锁只能用于隔离测试，不能作为生产的任务隔离方案。

另一个独立测试已证实： PostgreSQL 只读快照不能冻结磁盘资料，校验后原文件仍可能被替换。因此包含终态的只读预算显示保持待核，不能因分页成功就放行。不得推断现有代码已经支持无限历史或生产迁移。

## 已确认的写路径与锁序

以下是梳理出的直接相关路径，不是对部署环境全部版本、插件及数据库角色权限的完整证明。上线前还必须以运行清单、角色授权和 SQL 跟踪补齐未知写方。

| 写路径 | 已确认的顺序或问题 |
| --- | --- |
| v1 `same_goal_advice_store_v302.prepare/cancel` | 请求 nonce 锁 → Task 行锁 → 当前用户/成员与库存；修改 Plan、Job、审计。 |
| v1 `same_goal_advice_execution_v308.start`、`same_goal_advice_review_v308.review` | 请求 nonce → 任务及 Plan 锁 → 授权及原记录校验。 |
| v1 `same_goal_advice_options_v310.price/configure_quota` | 请求 nonce → Task 锁 → 选项审计。 |
| v1 `same_goal_advice_quota_v304.authorize` | Task 锁 → 当前人员及授权记录；该入口没有上述 nonce 锁，不能假设所有路径锁序相同。 |
| v1 worker `same_goal_advice_runtime_v308._owned/process` | 持任务、Plan 等锁检查所有权；外部调用/恢复处会提交并释放事务锁。跨外部调用不能假设原 Task 锁仍有效。 |
| 通用 `cloud_budget.finish_tx/settle_paid_response` | 以 CloudCall 锁和每日 Job 账目锁为核心，不以内置 Task 锁作为统一入口。收据结算必须连同实际调用方逐条改造，避免先锁 CloudCall 再等任务门锁造成逆序。 |
| 通用 `evidence` 写入 | 文件和 evidence 上传记录由通用服务处理；不能假定文件生命周期随 Task 数据库锁冻结，也不能仅通过上传审计推知其最终所属任务。 |
| v2 测试 `prepare_writer/preview/start`、`unlimited_lease` | 分别通过 nonce（如适用）→ Task → Plan/Job 等锁进入；仅可在专用测试数据库运行。 |
| v2 测试 `file_intent`、`prepare_document`、首答 custody/结算 | 还涉及 Job、Plan、文件、首答表、CloudCall、日账和审计；部分路径当前使用全表锁。它们不能直接升作任务隔离实现。 |

特别地，`same_goal_advice_common_inventory_v2` 除正向读取 Plan 外，还扫描审计、Job、调用及证据等反向孤儿；只给 Plan 做分页会漏掉异常历史。`same_goal_advice_read_session_v2` 还有限制已载入对象数的保护，必须和查询分页一起设计。旧版本、后台恢复任务、共享账目与资料写入均可能绕开新应用层锁，单纯修改新版读取器不足以消除竞争。

## 可执行迁移方案与交付门槛

1. **建立写方清单与停写边界。** 用代码搜索、所有进程及版本清单、专用环境 SQL 审计和数据库角色/权限核对覆盖 API、worker、重试/结算、资料和共享账目写方。特别识别数据库维护脚本、旧二进制和开放的直接 DML。无法确认或停止的写方即为上线阻碍。备份并演练恢复；旧请求和未知账单保持原样待核。
2. **建立任务归属和数据库执行边界。** 为任务记录建立可索引的 `(workspace_id, task_id, sequence)` 账本，追加条目与原 Plan、Job、审计、调用、首答和结算在同一事务落库；唯一键及外键保证跨工作区隔离、请求唯一和关系可追溯。每个可产生、更新或删除相关记录的路径均须在写前取得相同任务级数据库门锁，并以数据库权限隔离旧角色的直接写入；必要时使用受控数据库函数并固定 search_path、最小权限。共享 Audit 和 Evidence 的任务归属必须有明确、可反查的权威关联，不能只解析可选 JSON 字段或漏掉通用上传。对无法安全归属的历史保守待核。
3. **统一锁序再切换。** 从请求入口、worker 到 CloudCall 结算统一定义并测试 nonce、任务门锁、任务/计划/作业、调用和日账的获取顺序。不能在已持 CloudCall 或其他行锁后才引入可能与读方反向等待的任务门锁；行级触发器也不自动修复这一锁序。外部模型调用跨事务时重新取得门锁并核对原请求和已发送证明，不得重发不确定请求。切换时必须排空旧版本和进行中的事务并撤销其相关写权限；回滚不能恢复不遵守门锁的写方继续修改新账本。
4. **迁移历史而非伪造历史。** 对可证明的原记录按版本生成可校验关联，维持原始时间、调用与日账；缺失首答、用量、归属或发送结果时保持待核，不以补记终态、覆盖原记录或删除冲突来制造一致。迁移前后比较原始记录计数与哈希并验证可恢复；不要求对真实数据直接试验。
5. **稳定分页与反向核验。** 仅在上述写隔离生效后，在同一事务内按不可变唯一键做有界 keyset 分页，固定任务上界，逐页验证；利用索引化的数据库反向关联/反连接检查所有相关表的孤儿、重复和跨工作区引用，包括末页之后的异常，不使用全局表锁，也不把整张表移入应用内存。预先定义一致的读隔离级别及快照创建顺序；不同任务互不阻塞。只读展示还需不可变、版本化的资料存储与文件生命周期证明，数据库快照本身不够。
6. **仅在证明完整后开放。** 专用 PostgreSQL 用超过 1000 组有效历史，覆盖最后一页孤儿/篡改、旧版和新版混合、不同任务并行、同任务并发新建/撤销/结算、旧角色直接写入拒绝、重复请求、跨工作区、崩溃重启、资料替换和授权撤销。测量查询计划、内存及延迟；之后才可评估受控真实环境迁移。任一参与写方或文件一致性未验证时，保持当前关闭和 409 待核，不声称不限次数。
