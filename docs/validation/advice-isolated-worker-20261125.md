# 隔离环境业务建议链路验证记录

验证使用新建的本机临时 PostgreSQL、合成资料和本机固定响应服务；网络沙箱只允许本机测试端口，未使用真实模型密钥、真实报告或正式工作区。

真实本机 HTTP 完成登录、资料准备、两份资料授权、预览和用户确认，并启动独立 worker。该次测试总耗时 729 秒，在 worker 运行 240 秒后超时，未得到可验证结果。用户确认前的阶段耗时包括申请准备 53.07 秒、资料整理和幂等核对 44.53 秒、资料读取和状态核对 46.33 秒、资料授权 91.05 秒、预览 59.54 秒、确认 169.90 秒。上述耗时是实际产品可用性的阻碍。

超时前只读快照显示控制任务运行中，已有一条调用占位，未见派发许可；快照早于进程停止，不能证明最终是否发送。测试 runner、worker 和测试数据库均已退出；旧测试夹具将模型桩请求计数保存在内存，且退出时清理临时数据库，因此本次最终请求数和最终账本不可考。原申请按状态不明处理，不得自动重试。快照与日志仅保留在本机私有目录，不纳入版本库。

快速验证另行覆盖隔离 worker 启动、单次本机模拟发送、断线后的防重复、撤权与许可的双向并发锁，以及失败状态显示。这些采用合成来源或来源替身，不能替代上面的完整链路。正式迁移、持久卷、浏览器端流程、生产服务及模型实际业务价值均未验证；正式发送保持关闭。

为后续测试增加了专用留存 runner：仅允许独立测试数据库及本机端口；测试失败或超时时停止进程并保留私有数据库目录和本机桩请求元信息，记录不包含请求正文或密钥。测试正常退出时还会保留合成证据；若进程被强制终止，证据目录不一定能归集。完整请求到达后计数持久化；文件缺失或不完整时不能视作请求数为零。保留目录不会自动清理，必须由操作员核对后显式运行 `scripts/run_retained_user_advice_checkpoint.py --cleanup <测试目录>`；清理前检查目录标记、归属和数据库已停止。

本机桩另写私有 `provider-connections.json`，只记录监听状态与应用已接受的 socket 数；绑定后写入 `running`，每次接受后先完成原子替换及文件、目录同步再交给处理线程。写入失败时停止接收并使测试失败；仅在接收循环和处理线程均停止、写入成功后写入 `stopped`。只有结合测试进程成功结束及运行器状态，才可将 `stopped` 视作该桩的完整接受计数；中途崩溃、短连接、落盘失败和不完整状态均不能推断零请求。即使完整计数为零，也仅表示该桩未接受 socket，不能排除客户端连接尝试、内核排队、向其他服务发送或同一账号篡改文件；计数不授权重试，也不能证明真实模型调用状态。

隔离测试在 `timings.jsonl` 中按步骤保存资料链读取、库存核对、ORM 解码和完整校验的次数及累计耗时；`timings.jsonl.worker` 由独立 worker 每 5 秒记录一次同类数字指标，超时前的数据可用于定位。这些耗时是包含下层调用的时间，不可相加；输入长度是字符数，不含原文、SQL、标识、哈希或凭据。worker 被强制终止时最后一个区间可能缺失，不能用这些指标推断请求是否发送。此探针只供新的隔离合成运行使用，不改变正式代码，不对状态未知的原申请重试。

新增的 `result_processor` 包含外层 JSON 解析及内部解码；`orm_decode` 和 `full_verification` 为其嵌套计时。`session_execute`、`connection_execute` 和 `driver_execute` 记录调用次数和累计耗时，直到返回结果对象为止；它们可能互相嵌套，也不包括后续遍历结果所花的时间，不得相加或称作完整数据库查询耗时。失败调用同样计入次数，仅记录数字，不记录查询或参数。

连接执行来源只按测试启动时现有应用源码文件名构建固定白名单并分组；未识别模块归入其他，不记录动态模块名、堆栈、参数或业务标识。来源按最近一层应用模块分类，可能包含该模块调用的下层工作。

提供单独的 `--context-only` 合成诊断模式：恢复经核验的全新合成快照到新建测试库，仅登录及 GET 业务建议上下文；网络沙箱只允许该测试数据库出站，禁用云提供商和发送开关，并核对测试前后云调用为零、建议记录数量未增加。模式不执行资料授权、建议创建、发送或 worker，不能用来宣称完整链路通过。

同一模式另用独立合成表验证读一致性：READ COMMITTED 下，两个逐次授权范围查询之间如有并发提交，第二个查询可以看到新值，而提前合并为一次批量查询会保留较早值；该实验未修改业务记录，不支持直接以缓存或批查取代原核验。重复访问诊断使用进程内一次性随机密钥及限量临时集合，只输出聚合次数；摘要或密钥不写入文件，读取统计后清空并更换密钥。该统计只描述合成样例，不能证明跨阶段复用安全。

仅测试代码中的请求内纯解码缓存候选，使用一次合成上下文按基线、候选、基线、候选顺序执行四次只读请求：基线 12.49、12.05 秒，候选 11.19、11.39 秒；每次完整认证分别为 1062 与 751 次，数据库执行次数保持 2174。候选限定会话身份、线程与任务，缓存完整认证输入对应的不可变编码，读取时生成新对象；作用域结束清空。每次候选记账峰值 4,192,719 字节，进程总 RSS 高水位首次候选期间增加约 32.9 MB、第二次未增加；后者包含整个进程的分配，不能直接归因于缓存或证明实际额外内存上限。两组各仅两次，顺序、预热和探针开销可能影响结果。候选未接入生产；精确的实际额外内存、更多并发及真实业务效果仍未验证。

单独的 `--functions-only` 模式在全新隔离数据库中只执行一次登录和只读上下文 GET；只在同步请求处理函数内启用 cProfile，结果经固定源码函数白名单及固定其他类别汇总，原始 profile、路径、堆栈、参数和资料均不写入文件。一次合成请求中 `_json_value` 和 `_string` 分别被调用约 624 万次和 840 万次，`saved_execution` 18 次；剖析本身使请求耗时约 26.7 秒，不可与未剖析请求直接比较。函数累计时间包含下层调用，不可相加。这表明存在重复核验线索，并不证明可跨阶段安全复用；当前权限、原件校验、并发与锁边界仍须保持。

`--tamper-only` 模式只在新建隔离库的合成记录上做并发反例：`guard → validate_document_sources → saved_execution` 返回后，另一事务破坏合成发布记录的认证摘要；同一 `guard` 内第二次 `saved_execution` 检出不一致并返回 409。该检查点没有云调用或新增建议，测试进程与数据库均已停止。直接合并这两次读取会失去该时点的篡改检测，不是等价优化，故未修改生产路径。

留存夹具已使用独立的小型故意失败测试验证：数据库与合成证据留存，停止的数据库可在只读模式下恢复并读取合成记录，显式清理有效。另以短超时验证超时状态和停止后的目录留存；模型桩元信息的异常退出与兼容性测试共 5 项通过。未重新运行长链或重发原申请。
